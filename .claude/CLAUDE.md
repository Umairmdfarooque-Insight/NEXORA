# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Nexora is the AI engine behind a UI called "Rayfin" (`APP_NAME` / `UI_APP_NAME` in `app/config.py`). It takes a business requirement in plain English and works out which tables and columns in a Microsoft Fabric Lakehouse can satisfy it. The sample data is AdventureWorks-style (`saleslt` schema).

## Spec and design docs

The target product is defined in `.claude/spec/` (requirements FR/NFR, business rules, acceptance scenarios) and `.claude/technical-documentation/` (architecture, artifact contracts, run states, gates G1–G6, milestones, open decisions). Both are transcribed from `Nexora_Specification_and_Technical_Design.docx` (v0.1 draft). Read them before adding a new pipeline stage.

The code is an early slice of the design and does not yet produce its artifacts. Mapping of current code to the design:
- `requirement_analyzer.py` → the old prototype of the Requirement Compiler. The real one is `app/compiler/` (T-202): it produces `BusinessContract.yaml`. The approval loop comes with T-203/T-204.
- `metadata_inventory.py`, `data_profiler.py`, `semantic_mapper.py`, `relationship_validator.py` → Metadata Harvester and relationship evidence (M3, FR-005–FR-007).
- Not started: the Rayfin UI and run store (M1), planning (M4), TMDL/DAX (M5), reports (M6), retries, deployment and audit (M7).

Manual test steps for every finished task are in `.claude/MANUAL_TESTING.md`; `/implement-task` updates it at each hand-over.

The human workflow (dev session `T-xxx` plus review session `T-xxx_test`, task branch, PR, cleanup) is described in `.claude/DEVELOPMENT_WORKFLOW.md`. In a `_test` session, review and help test only; don't implement the task. Use `/review-task [T-xxx]` (`.claude/skills/review-task/SKILL.md`) for the review. The build order is in `.claude/tasks/` (T-001 … T-706, grouped by milestone M0–M7). Each task has six sections (problem statement, functional requirements, API contracts, constraints, edge cases and error handling, acceptance criteria). Its acceptance criteria must pass a manual test before the next task starts. Shared shapes and error codes are in `.claude/tasks/CONTRACTS.md`; implement against them exactly. `.claude/tasks/README.md` lists the defaults assumed for the spec's open decisions, such as FastAPI, hybrid orchestration and a file-based run store. Orchestration is decided as **hybrid**: the run state machine and `RunStore` own run state, approvals and audit, and LangGraph stage graphs run only the LLM loops inside a stage (rules in `.claude/tasks/CONTRACTS.md#stage-graphs`). Use `/implement-task <milestone file | task ID>` (`.claude/skills/implement-task/SKILL.md`) to work on a task. It enforces the dependency order and keeps the README status column up to date. Use `/commit-push [branch | "note"]` (`.claude/skills/commit-push/SKILL.md`) to commit with a generated message and push. The repo is public, so that skill blocks secrets and binaries. After a branch's PR is merged, `/cleanup-branch [branch]` updates local `main` from the remote and deletes the branch, after a caution message and confirmation.

Rules from the spec that constrain all new code:
- The LLM proposes; deterministic validators decide progression.
- No silent assumptions for KPI definitions.
- Return "Not Feasible / Data Gap" instead of fabricating a calculation.
- A LangGraph stage graph never changes run state or writes `RunManifest.json`. Its loops are bounded, and it routes only on validator output.

## Commands

Windows; a virtualenv lives in `.venv` (Python 3.12). A `.venv` copied from another machine fails with "No Python at ..."; recreate it with `py -3.12 -m venv .venv`.

```
.venv\Scripts\activate
pip install -r requirements.txt           # lists every third-party package the code imports
python -m app.test_requirement_analyzer   # run one script
python -m app.tools.smoke [--only llm,lakehouse,sql] [--json]   # check LLM, Lakehouse and SQL access; exit 0/1/2
python -m app.cli runs create --prompt "..."   # also: list, show RUN_ID, transition RUN_ID STATE (exit 0/1/2)
python -m app.cli contract validate FILE   # VALID/INVALID (exit 0/1); also: contract schema [--output FILE]
python -m app.cli plan validate runs/RUN_ID   # check ModelSpec.yaml and ExecutionPlan.yaml: VALID/INVALID (exit 0/1/2)
python -m app.cli model generate runs/RUN_ID   # write the next TMDL version of a run: runs/RUN_ID/model/v<n>/ (exit 0/1/2)
python -m app.cli deploy model TMDL_DIR --name NAME   # create or update a semantic model in the sandbox workspace (exit 0/1/2)
uvicorn app.api.main:app --reload --port 8000   # orchestration API; Swagger at /docs
cd rayfin-ui; npm install; npm run dev          # Rayfin UI on http://localhost:3000 (also: npm test, npm run typecheck, npm run build)
```

- Test data for the acceptance scenarios lives in schema `nexora_test` of the sandbox Lakehouse. It is created by the Spark notebook `fixtures/create_test_tables.ipynb` (see `fixtures/README.md`), not by Python in `app/`. `python -m app.test_metadata_inventory [schema]` lists a schema's tables (default `saleslt`).
- There is no build, lint, or pytest setup. The `app/test_*.py` files are **manual scripts** with a `main()`. Each exercises one pipeline stage against live Azure/Fabric.
- Run them as modules from the project root (`python -m app.test_x`). Imports are absolute (`from app.config import ...`), so running the file directly will fail.
- Running anything needs a `.env` (copy `.env.example`). `app/config.py` loads `PROJECT_ROOT/.env` once (shell variables win over `.env`, so the working directory doesn't matter) and calls `get_required_setting` at import time for `AZURE_OPENAI_ENDPOINT`, `AZURE_OPENAI_DEPLOYMENT` and `AZURE_OPENAI_API_KEY`, so importing `app.config` raises `ValueError` if any is missing. That includes the connector modules. The Fabric settings (`FABRIC_*`) are optional: `get_optional_setting` returns `None` when they are unset or blank.
- Fabric access goes through `app/auth.py`: one process-wide `InteractiveBrowserCredential` with an on-disk token cache (`TokenCachePersistenceOptions(name="nexora")`), plus a saved sign-in record (`%LOCALAPPDATA%\.IdentityService\nexora_auth_record.json`, account identifiers only, no tokens), so a process signs in once and later runs read the cache silently. Delete that file to force a fresh sign-in. Connectors call `get_token(STORAGE_SCOPE | SQL_SCOPE | FABRIC_SCOPE)`; never create a credential elsewhere. `fabric_sql_connector` also needs the ODBC Driver 18 for SQL Server installed.

## Runs

`app/workflow/` holds the run states (`states.py`) and the `Run` model with the single `apply_transition` function (`run.py`). `app/store/` holds the `RunStore` interface (`base.py`), the default `FileRunStore` (`runs/<run_id>/RunManifest.json`, gitignored) and `SqlRunStore` (table `dbo.nexora_runs` in a writable Fabric SQL Database). `RUN_STORE=file|fabric_sql` picks the store through `get_run_store()`; `fabric_sql` also needs `FABRIC_CONTROL_DB_SERVER` and `FABRIC_CONTROL_DB_NAME`. Only the store writes manifests.

`app/api/` is the FastAPI orchestration API (`main.py` app, CORS for `http://localhost:3000`; `runs.py` routes; `schemas.py`; `errors.py` maps exceptions to the shared error envelope; `deps.py` supplies the store). Handlers hold no business logic and there is no public state-transition endpoint. `app/workflow/next_action.py` maps each state to its `next_action`. Every endpoint except `/health` needs an Entra bearer token (`api/security.py` validates signature, issuer, audience, expiry, tenant and the `access_as_user` scope; `current_user` yields `{oid, upn, name}`). There is no bypass: without `ENTRA_TENANT_ID` and `ENTRA_API_CLIENT_ID` protected endpoints return `500 CONFIG_ERROR`. Fabric and OneLake are called on behalf of the user (`api/obo.py`, MSAL OBO; needs `ENTRA_API_CLIENT_SECRET`), so lists reflect that user's access. Runs record `created_by` and the history actor as the user's UPN. The CLI calls the store directly and needs no token.

Fabric access for runs: `connectors/fabric_api.py` (`FabricApiClient`) lists workspaces and Lakehouses (paging, 429 retry, typed errors); `workflow/scope.py` (`bind_scope`) verifies and saves a run's `scope` (`PUT /runs/{id}/scope`, locked once metadata is harvested). Connectors take the scope through `FabricLakehouseConnector.for_scope(scope)` and `FabricSQLConnector.for_scope(scope)`; with no scope they fall back to the `FABRIC_*` values in `.env`.

`rayfin-ui/` is the Rayfin web UI: Next.js (app router), TypeScript and Fluent UI v9. Pages: `/runs` (list), `/runs/new` (prompt, scope and options form), `/runs/[id]` (state, next action, open questions, scope, timeline, and the clarification panel with Compile, answer and dismiss), `/runs/[id]/contract` (contract review: KPIs with inline edit, G1 checklist, Accept / Reject / Explain / Regenerate, approval history), `/runs/[id]/inventory` (inventory: harvest, profile and analyze buttons, G2 checklist with Accept, source exceptions, data gap, searchable and paged table list with column profiles, warnings that show their queries, relationship evidence; display rules in `src/lib/inventory.ts`), `/runs/[id]/plan` (plan review: prepare buttons, G3 checklist with Accept / Reject, storage mode, tables with their rationale and rejected alternatives, relationships with evidence and SQL plus Remove / Override, measures with Remove, data-engineering actions with owner, approval history; display rules in `src/lib/plan.ts`). Display rules live in `src/lib/review.ts` (unit-tested with `npm test`); every edit and approval sends the `BusinessContract` hash from `run.artifacts` as `expected_hash`, and actions the user's roles don't allow are hidden (roles come from `GET /me`). All data comes from the API through `src/lib/api.ts` (`NEXT_PUBLIC_API_BASE_URL`, default `http://localhost:8000`, set in the gitignored `rayfin-ui/.env.local`); the UI holds no business logic. The UI signs in with MSAL (`src/lib/auth.ts`, `src/components/AuthProvider.tsx`) before any page renders and sends the token as a bearer header (`src/lib/api.ts` refreshes it silently once on `TOKEN_EXPIRED`). Settings: `NEXT_PUBLIC_ENTRA_TENANT_ID`, `NEXT_PUBLIC_ENTRA_CLIENT_ID`, `NEXT_PUBLIC_API_SCOPE`. The API's CORS allows only `http://localhost:3000`, so the UI must run on that port.

## Business contract

`app/contracts/business_contract.py` defines `BusinessContract` (pydantic, `extra="forbid"`) and its parts (`Kpi`, `OpenQuestion`, `LockedFact`, `Feasibility`). `load`/`save` read and write `BusinessContract.yaml` deterministically (fixed key order, UTF-8, LF; `save` returns the `sha256:` hash). The approval rules (no open blocking question; every KPI has `formula_intent`, `grain` and `currency`; unique KPI names and ids) live in the model, not in prompts. `schemas/business_contract.schema.json` is the committed JSON Schema (regenerate with `contract schema --output`); `samples/contract_valid.yaml` is the reference sample. 

### Requirement Compiler (T-202)

`POST /runs/{id}/compile` (`workflow/compile_stage.py`, `compile_run`) is allowed in `CREATED` and `NEEDS_CLARIFICATION` only (`409 WRONG_STATE` otherwise). It runs the `compile` LangGraph (`graphs/compile.py`, run through `graphs/base.py:run_graph`): `llm_compile → validate_schema → (one retry with the errors) → apply_critical_terms → apply_locked_facts`. The LLM call (`llm/structured.py`, Responses API, strict JSON Schema, 60 s) gets only the prompt, subject area, outputs, constraints and the previous contract. `config/critical_terms.yaml` lists the business-critical terms; one used without a definition always gets a blocking `RULE-<TERM>` question (`compiler/critical_terms.py`), and no KPI gives `RULE-METRIC`. The service writes `runs/<id>/BusinessContract.yaml` and `contracts/BusinessContract.v<n>.yaml`, registers the artifact and moves the state (`NEEDS_CLARIFICATION` while a blocking question is open, else `CREATED`). The graph itself never touches run state. Tests inject a fake LLM through `build_compile_graph(llm=…)` or the `get_llm` dependency.

### Clarification loop (T-203)

`workflow/clarification.py` holds the three actions; `api/runs.py` only calls them. `POST /runs/{id}/questions/{qid}/answer` stores the answer, replaces the locked fact `LF-<qid>` and recompiles through `compile_run(previous=…)`, so the state moves `NEEDS_CLARIFICATION ⇄ CREATED`. If the recompile fails nothing is saved. `…/dismiss` closes a non-blocking question (`status: dismissed`, `dismiss_reason`; a blocking one gives `409 QUESTION_CONFLICT`) and `PUT /runs/{id}/contract/kpis/{kpi_name}` applies a partial KPI edit guarded by `expected_hash` (`409 STALE_VERSION`). Both write a new contract version without the LLM and leave the state alone. All three give `409 CONTRACT_LOCKED` once the contract is approved, and `409 WRONG_STATE` outside `CREATED`/`NEEDS_CLARIFICATION`. `apply_locked_facts` also carries dismissed questions and re-applies a term's locked fact as the `formula_intent` of the first KPI that mentions the term; an override of a different LLM value is written to `logs/compile-<ts>.json` as a warning. An edit of that `formula_intent` updates the fact, so recompiles keep the owner's text.

### Approval and Gate G1 (T-204)

`workflow/approval.py` (`perform`) is the reusable approval service; the routes in `api/runs.py` only call it (`POST /runs/{id}/approvals`, `GET /runs/{id}/approvals`, `POST /runs/{id}/gates/G1/check`). Only `BusinessContract` is supported so far (other artifacts give `422`). `workflow/gates.py` holds `GateResult` and `run_g1` (checks G1.1–G1.5, deterministic); results are saved to `runs/<id>/gates/G1-<timestamp>.json`. Accept runs G1 (`409 GATE_FAILED` lists the failed checks), writes the contract as the next version with `status: approved`, and moves `CREATED → REQUIREMENT_APPROVED`. Reject adds a blocking `REV-<n>` question (`source: reviewer`, kept open across recompiles) and moves the run to `NEEDS_CLARIFICATION`. Explain is deterministic text, with no LLM. Regenerate recompiles with the comment as guidance and keeps the locked facts. Every successful action appends a record to `runs/<id>/approvals.jsonl`. Roles come from the committed `config/roles.yaml` (`workflow/roles.py`, read on every request, UPNs matched ignoring case); only `business_owner` may Accept or Reject, and a missing or invalid file is `500 CONFIG_ERROR` (checked at API startup too).

`RunDetail` (from `GET /runs/{id}` and every action that returns a run) carries `contract` (the current `BusinessContract`, or `null`) and `artifacts`, so the UI needs no separate contract call. `GET /me` (`api/me.py`) returns `{oid, upn, name, roles}` from `config/roles.yaml`.

### Metadata Harvester (T-301)

`POST /runs/{id}/harvest` (`workflow/harvest_stage.py`, `harvest_run`; a plain function, no graph) reads the run's scope through the OneLake table API (`discovery/harvester.py`, no LLM) and writes `runs/<id>/MetadataInventory.json` plus `inventories/MetadataInventory.v<n>.json` (models in `contracts/metadata_inventory.py`). Allowed in `REQUIREMENT_APPROVED` and in `DATA_PROFILED` (a re-harvest, which moves the run back to `REQUIREMENT_APPROVED`); `409 WRONG_STATE` otherwise, `400 BAD_REQUEST` if the run has no scope. The body's `schemas` overrides `scope.schemas` for that harvest only (empty scope and no body means all schemas; an unknown one is `404 SCHEMA_NOT_FOUND` and nothing is written). A table that fails is recorded in the inventory's `errors[]` (`FORBIDDEN`, `NOT_FOUND`, `RATE_LIMITED`, `UPSTREAM_TIMEOUT`, `UPSTREAM_ERROR`, `NO_COLUMNS`) and the rest are still harvested. A new version resets `profile` and `relationship_evidence`. The inventory also has a `warnings` list (for example 0 tables). `GET /runs/{id}/inventory` returns the current file (`404 NOT_FOUND` before the first harvest). `FabricLakehouseConnector.list_tables` follows `next_page_token`.
### Data profiler (T-302)

`POST /runs/{id}/profile` (`workflow/profile_stage.py`, `profile_run`; a plain function) runs `discovery/data_profiler.py:profile_tables(connector, inventory, tables)` over the Lakehouse SQL endpoint, as the signed-in user (`api/deps.py:get_sql_connector_factory`, OBO with `SQL_SCOPE`; `FabricSQLConnector` takes a `token_provider`). Tables are the candidates (contract `entities` matched to table names with the glossary's `aliases_for` (`config/glossary.yaml`) and `normalize`, in `candidate_tables`) plus any `{"tables": ["schema.table"]}` in the body (`404 NOT_FOUND` if not in the inventory). Allowed in `REQUIREMENT_APPROVED` and `DATA_PROFILED`; the state never changes (T-304 moves it). It needs a harvested inventory (`404 NOT_FOUND` otherwise) and a scope with a SQL endpoint (`400 BAD_REQUEST`). Only `SELECT`s, identifiers bracket-quoted from the inventory, 120 s statement timeout, `APPROX_COUNT_DISTINCT` and `approximate: true` above 10M rows. Profiles go into `tables[].profile` of `MetadataInventory.json` (and the same-version copy), merged with earlier ones; the harvest version stays and the artifact hash changes. A table that fails gets `status: error` with a `code` (`TABLE_NOT_FOUND`, `QUERY_TIMEOUT`, `QUERY_FAILED`) and the others continue. No row values are stored: min and max only for date and numeric columns. `duplicate_count` is the number of values that appear more than once, as in `GROUP BY … HAVING COUNT(*) > 1`.
### Relationship evidence (T-303)

`POST /runs/{id}/relationships/analyze` (`workflow/relationship_stage.py`, `analyze_run`; a plain function) collects candidate joins, measures each one over the SQL endpoint (as the user, like the profiler) and stores `RelationshipEvidence` in `MetadataInventory.relationship_evidence`, replacing the previous list. `GET /runs/{id}/relationships` returns it (`[]` before the first analysis; a re-harvest clears it). Same states and preconditions as the profiler; the run state never changes. Candidates (`discovery/relationship_candidates.py`): naming heuristics (`XxxID` in one table to `XxxID` or `ID` in a table whose underscore-separated name contains `Xxx`), the LLM (`get_relationship_llm`, strict JSON schema, sees the contract and table and column names and types only, never data) and an optional body `{"candidates": [{"from": {"table", "column"}, "to": {...}}]}` (`source: user`). A failing LLM only adds a `warnings` entry; the other candidates are still analyzed. Evidence (`discovery/relationship_evidence.py`, thresholds in `config/relationship_thresholds.yaml`): type compatibility, `overlap_pct` (distinct non-null source values found in the target), `orphan_rate` (non-null source rows with no match), `null_rate`, `cardinality` and `confidence`; percentages are 0-100. A target column that isn't unique is never better than `low` (`require_unique_target`). A type mismatch runs no join query. Rejected (`status: rejected`, `rejected_reason`): unknown table or column ("table not in inventory", "column not in inventory"), a self-relationship, a table that can't be profiled ("profile missing"), a failed query. Tables a candidate uses are profiled first if they have no profile. At most 200 candidates are analyzed. The response `candidates` counts the non-rejected ones (`high + medium + low`).
### Gate G2, exceptions and data gaps (T-304)

`workflow/inventory_review.py` holds the G2 service; the routes in `api/runs.py` only call it. `POST /runs/{id}/gates/G2/check` runs `gates.run_g2` (G2.1-G2.5, deterministic) on the run's *candidate tables*: the harvested tables that match a contract entity (`data_profiler.candidate_tables`), plus matching tables that failed to harvest (`candidate_error_tables`, so a 403 table can't be skipped). No candidates fails G2.1. G2.4 is a `warning`, never a `fail`. The approved conformed sources are in `config/conformed_sources.yaml` (`workflow/conformed.py`, read on every call, `500 CONFIG_ERROR` if invalid); a candidate outside it needs an exception (G2.5). `POST /runs/{id}/exceptions` (`{"table", "rationale"}`, role `data_engineer`, `201`) records an approval record with artifact `Exception:<schema.table>` and the rationale as comment; a table that isn't a candidate is `422`. `POST /runs/{id}/approvals` with `{"artifact": "MetadataInventory", "action": "ACCEPT", "expected_hash": <inventory hash>}` needs the `data_engineer` role, state `REQUIREMENT_APPROVED`, a passing G2 (`409 GATE_FAILED`) and a current hash (`409 STALE_VERSION`); it marks the inventory artifact `approved` and moves the run to `DATA_PROFILED`. Other actions on the inventory are `422`. A re-harvest returns the run to `REQUIREMENT_APPROVED` with a draft inventory, so G2 runs again. `POST /runs/{id}/data-gaps` (`{"description"}`, any user, states `REQUIREMENT_APPROVED` and `DATA_PROFILED`) appends to `runs/<id>/data_gaps.jsonl` and moves the run to `NEEDS_INPUT` (`resume_state` kept); `RunDetail.data_gaps` lists them. There is still no endpoint that leaves `NEEDS_INPUT` (use `python -m app.cli runs transition RUN_ID STATE`).
### Source resolution (T-401)

`POST /runs/{id}/plan/sources` (`workflow/source_stage.py`, `resolve_sources`; a plain function) writes `runs/<id>/SourceResolution.json` plus `resolutions/SourceResolution.v<n>.json` (models in `contracts/source_resolution.py`) and returns it. Allowed in `DATA_PROFILED` only (`409 WRONG_STATE`); it needs the harvested inventory and the contract; the state never changes. `config/glossary.yaml` (`discovery/glossary.py`, read on every call, `500 CONFIG_ERROR` naming file and line) replaces the old `ALIASES` dict: `Glossary.aliases_for(entity)` gives the words that name an entity, and `data_profiler.matching_keys` (G2 candidates), the old matcher and the resolver all use it. `discovery/source_resolver.py` holds the rules. Candidates per entity are glossary name matches (exact table name 1.0, a run of the words in the name 0.7; a schema-wide prefix such as `SalesLT_` is ignored) plus the model's suggestions (`get_source_llm`, strict JSON schema, sees the contract, glossary and table/column names and types only). A suggested table or column that is not in the inventory is discarded and logged. Score: `0.4·name_match + 0.3·column_coverage + 0.2·conformed + 0.1·relationship_confidence`, rounded to 2 decimals; ties go to conformed, then table name. A non-conformed table is eligible only with an approved exception (`inventory_review.approved_exception_ids`; the approval id is `exception_id`). Otherwise it is rejected with `requires_exception: true`, and if nothing is eligible `selected` is `null` with a `reason`. `kpi_fields` maps each KPI need the model lists to one column (selected tables first, conformed or excepted tables only). Needs that can't be mapped go in `unmapped` with a reason, which T-402 turns into data gaps. The model's raw answer is kept in `runs/<id>/source_suggestions.json`, keyed by a hash of the request, so unchanged inputs give an identical file; the version grows only when the content changes. An unusable model answer is `502 LLM_INVALID_OUTPUT` and nothing is saved.
### KPI feasibility and Data Gap (T-402)

`POST /runs/{id}/plan/feasibility` (`workflow/feasibility_stage.py`, `check_feasibility`; a plain function with one bounded retry) returns `{"kpis": [Feasibility], "run": RunDetail}` and writes `runs/<id>/Feasibility.json` (`contracts/feasibility_report.py`: `schema_version`, `version`, `based_on`, `kpis`; copies in `feasibility/`). Allowed in `DATA_PROFILED` only (`409 WRONG_STATE`); it needs `SourceResolution.json` (`404 NOT_FOUND` before `/plan/sources`). `discovery/feasibility.py` holds the rules. The model (`get_feasibility_llm`, strict JSON schema; sees the KPI definitions and the names and types of the columns SourceResolution maps, never data) lists each KPI's needs and the mapped column that could supply each (`schema.table.column` or null). Code has the final say (`evaluate`): a need is met only if its column is mapped in `SourceResolution` and still in the inventory, and a `time` need needs a date type. Needs that `SourceResolution.unmapped` lists count as missing even if the model omits them, and a KPI with `time_logic` but no time need gets a missing "date column for time logic". One missing need makes the KPI `data_gap` (never partly feasible; options `drop_kpi`, `provide_source`, `data_engineering_task`), and no proxy or partial measure is produced. Any data gap records one entry per KPI in `data_gaps.jsonl` (`inventory_review.raise_data_gaps`) and moves the run to `NEEDS_INPUT` (`resume_state: DATA_PROFILED`); nothing in `/plan/...` leaves `NEEDS_INPUT` (use `python -m app.cli runs transition RUN_ID DATA_PROFILED`). The model's accepted answer is kept in `feasibility_suggestions.json` (shared helper `workflow/llm_cache.py`), so unchanged inputs give an identical file and version; unusable output is retried once with the problem named, then `502 LLM_INVALID_OUTPUT` with the state unchanged and nothing saved. The artifact status is `data_gap` or `draft`.
### Bridge tables (T-403)

`POST /runs/{id}/plan/bridges` (`workflow/bridge_stage.py`, `propose_bridges`; a plain function, no LLM) returns `[BridgeProposal]` and writes `runs/<id>/BridgeProposals.json` (`contracts/bridge_proposal.py`; copies in `bridges/`; artifact `BridgeProposals`, status `draft`, `needs_input` while a `needs_rules` proposal is open, `approved` when all are). Allowed in `DATA_PROFILED` only (`409 WRONG_STATE`); it needs `SourceResolution.json` (`404`), a scope with a SQL endpoint and stored relationship evidence (`400 BAD_REQUEST`, run `/relationships/analyze` first). `discovery/bridge_detection.py` holds the rules, for the entities SourceResolution selected. A *mapping table* is an inventory table that no entity selected, whose every column joins with medium or high confidence into tables selected for entities, and that joins into at least two of them. A direct `many_to_many` evidence between two selected tables also needs a bridge; one between tables no entity uses is ignored and logged. An entity whose table joins to nothing is isolated, which gives one `needs_rules` proposal listing the other entities too. Per pair: the mapping table with the highest summed coverage becomes `existing_table` (evidence: `duplicate_pairs`, `coverage_a_pct`, `coverage_b_pct`, the aggregate-only `queries`; the other candidates and duplicates go in `issues`), else an approved rule from `config/derivation_rules.yaml` (`discovery/derivation_rules.py`, read on every call; `deduplicate: true` rules only allow duplicate pairs) becomes `derivation_rule`, else `needs_rules`: no table is proposed, a data gap asks for the mapping rules and the run moves to `NEEDS_INPUT`. A re-run keeps the id and decision of an unchanged proposal. `POST /runs/{id}/approvals` with `artifact: "BridgeProposal:<id>"` (`ACCEPT` or `REJECT` only; `expected_hash` is the `BridgeProposals` artifact hash) needs `bi_engineer` or `business_owner`, state `DATA_PROFILED` or `NEEDS_INPUT`; a `needs_rules` proposal, or one with duplicate pairs and no deduplication rule, gives `409 MAPPING_RULES_REQUIRED`; an approved one gives `409 ALREADY_APPROVED`. Each decision is a new `BridgeProposals` version and an approval record. T-401's name matching now counts a table as named by a word only if that is the whole name or the name after one leading qualifier (`dim_`), so `bridge_product_promotion` is not "promotion".
### ExecutionPlan and ModelSpec (T-404)

`POST /runs/{id}/plan` (`workflow/plan_stage.py`, `generate_plan`; a plain function, deterministic, no LLM) returns `{"execution_plan", "model_spec", "validation"}` and writes `runs/<id>/ModelSpec.yaml` and `ExecutionPlan.yaml` (models and YAML save/load in `contracts/model_plan.py`, `extra="forbid"`; copies in `plans/`; artifacts `ModelSpec` and `ExecutionPlan`, status `draft`; the plan's `based_on` is the model's hash). `GET /runs/{id}/plan` returns the saved files, validated again, in any state. POST is allowed in `DATA_PROFILED` only (`409 WRONG_STATE`). It needs `SourceResolution.json` and `Feasibility.json` (`404`), reads `BridgeProposals.json` if there is one, and gives `409 NO_FEASIBLE_KPIS` if every KPI is a data gap. The state never changes (T-405 moves it). `discovery/model_planner.py` builds the plan:
- **Tables:** the facts (tables of feasible KPIs' `measure` fields, grain from the KPI), the sources selected for the entities, the other tables the KPIs need, existing bridge tables and the date table.
- **Relationships:** only stored evidence of medium or high confidence (`many_to_one` or `one_to_one`, between tables in the model); `evidence_ref` is the evidence id.
- **Measures:** only feasible KPIs (`dax: null`, `description: "Approved: <formula intent>"`, format from the currency).
- **RLS and storage:** roles come only from `contract.security` (`RLS<n>`, no filter); storage mode is `DirectLake`.
- **Date table:** added when a KPI has time logic or a time field: a conformed table named for dates with a date column. If there is none, a blocking `data_engineering_actions` entry `create_date_table` is added and no calculated table. A bridge proposal without a physical table becomes a `create_bridge_table` action. A relationship to the date table needs evidence like any other, so ask `/relationships/analyze` for it as a user candidate.

`discovery/plan_validation.py` runs PLAN.1-PLAN.10: references, evidence or an override with a rationale, unique names and no double relationships, no calculated tables under Direct Lake, conformed sources, feasible measures, no DAX yet, RLS only from the contract, a date table or action, and connectivity as a warning. Each failure names its path, for example `relationships[Sales_Product].to.column: Product.NoSuchColumn`. The sandbox target is `FABRIC_SANDBOX_WORKSPACE_ID` (optional, in `.env.example`) or else the run's workspace. A re-run keeps the versions when nothing changed; an unreadable hand-edited file is regenerated as the next version.
### Gate G3, plan edits and approval (T-405)

`workflow/plan_gate.py` holds `run_g3` and `workflow/plan_review.py` the service; the routes in `api/runs.py` only call it. `POST /runs/{id}/gates/G3/check` runs G3.1-G3.7 on the current files and saves `gates/G3-<ts>.json` (artifact `ExecutionPlan`, hash = the plan artifact's hash):
- **G3.1:** every fact table has a grain, and there is a fact table.
- **G3.2:** every plan source is conformed or has an approved exception, read from the config and approvals now.
- **G3.3:** every relationship has evidence of medium or high confidence, or an override with a rationale.
- **G3.4:** stage dependencies resolve, there is no cycle, and G3 has an approver entry.
- **G3.5:** no open blocking `data_engineering_actions`; the failure lists each action with its owner.
- **G3.6:** every measure maps to a feasible KPI, and the tables its KPI needs (and the date table for time logic) are connected to the measure's table through relationships, so removing a needed relationship names the measure.
- **G3.7 (an addition):** the plan's references resolve, names are unique and there are no calculated tables under Direct Lake.

`PATCH /runs/{id}/plan` (`{"expected_hash": <ExecutionPlan hash>, "ops": [...]}`, any signed-in user, state `DATA_PROFILED`) applies the operations `remove_relationship {name}`, `set_storage_mode {value: DirectLake|Import}`, `override_relationship {name, rationale}` and `remove_measure {name}` in order. Any invalid one saves nothing: an unknown name is `422`, an unknown `op` is `422` listing the valid tags, a stale hash is `409 STALE_VERSION`. It writes new versions of both files (older ones stay in `plans/`), records an `EDIT` approval whose comment lists the operations, and returns `{model_spec, execution_plan, gate_result}`. Regenerating with `POST /plan` replaces edits. `POST /runs/{id}/approvals` with `artifact: "ExecutionPlan"` needs the `bi_engineer` role (`403` otherwise). `ACCEPT` needs state `DATA_PROFILED`, a current hash and a passing G3 (`409 GATE_FAILED`), marks `ExecutionPlan` and `ModelSpec` approved and moves the run to `PLAN_APPROVED`; a second one is `409 ALREADY_APPROVED`. `REJECT` needs a comment and records it; on an approved plan it also reopens it (`PLAN_APPROVED` to `DATA_PROFILED`, artifacts back to `draft`). `GET /runs/{id}/plan/sources` returns the saved `SourceResolution` (rationale and rejected tables for the screen).

### Bridge-table generation (T-506)

`POST /runs/{id}/model/bridges/{bridge_id}/generate` (`workflow/bridge_model_stage.py`, `generate_bridge`) returns `{"version", "validation"}` (the new TMDL version and its Gate G4 run). Allowed in `MODEL_GENERATING` only (`409 WRONG_STATE`); an unknown bridge is `404`, a `needs_rules` proposal `409 MAPPING_RULES_REQUIRED`, a proposal that isn't `approved` `409 BRIDGE_NOT_APPROVED`. The two entity sides come from `SourceResolution` and the strong relationship evidence (`model/bridge_model.py:find_sides`); a bridge needs both entity tables in the model (`422` otherwise).
- **`existing_table`:** the mapping table becomes a `bridge` table of the ModelSpec with two `many_to_one` relationships from the bridge to the entity tables (one-to-many from each dimension), the key columns hidden, `evidence_ref` of the T-403 evidence. Filter directions are fixed by `apply_bridge`: the relationship to the entity table that is related to a fact table is `both`, the other `single`, so a filter on the other entity flows other → bridge → anchor → fact. If the proposal has duplicate pairs it needs its approved `deduplication_rule` (else `409 MAPPING_RULES_REQUIRED`); a deterministic notebook then materializes a `SELECT DISTINCT` copy.
- **`derivation_rule`:** the model (`get_bridge_llm`, strict JSON schema; sees the rule text and table and column names and types only, never data; tables in `nexora_generated` are left out) drafts one Spark SELECT, and code accepts only a single read-only SELECT over inventory tables with no literal the rule doesn't state (`model/bridge_sql.py`, 2 attempts, saved in `bridge_suggestions.json`; refusal is `422`). The relationships carry an `override_rationale` naming the rule.
- **Notebook** (`model/bridge_notebook.py`): `runs/<id>/bridges/<bridge_id>.ipynb`, deployed to the sandbox workspace with `FabricItemsClient.upsert_notebook` and run with `run_notebook` (job type `RunNotebook`, polled; a failed run is `NotebookRunFailed` with the run id, `502 UPSTREAM_ERROR`, and nothing else changes). It only creates `nexora_generated.<table>` in the Lakehouse it is attached to, fails on an empty result, and is only allowed when the run's Lakehouse is in the sandbox workspace (`403 TARGET_NOT_ALLOWED`). The new table is harvested into the inventory (columns checked against the expected ones) before it is used.
- The candidate ModelSpec is checked with the plan validation before it is saved as the next version; then T-502 writes the next `model/v<n>` and `run_validation` runs Gate G4 (a failure moves the run to `MODEL_FAILED`). **G4.BRIDGE.UNIQUE** (no duplicate pairs, with up to 5 shown; an empty bridge fails), **G4.BRIDGE.ORPHANS** (per side; above `medium.orphan_rate_max` fails, any orphans warn) and **G4.BRIDGE.TOTALS** (each measure's grand total equals the one in the latest passing validation of an earlier version; with no earlier validation it warns `NO_BASELINE`) run for every table of role `bridge` in every validation (`model/bridge_checks.py`), so `POST /model/validate` re-checks them.

### Repair service (T-505)

`POST /runs/{id}/model/repair` (`repair/service.py`, `repair`) returns `{"attempts", "final_state", "outcome", "message"}` (`repair/models.py`). Allowed in `MODEL_FAILED` only (`409 WRONG_STATE`); a latest validation with no failed check is `409 WRONG_STATE` "Nothing to repair"; any `artifact` but `SemanticModel` is `422` (the `Report` adapter comes with T-603). It runs the `repair` graph once (`graphs/repair.py`, generic; the artifact-specific part is the adapter in `repair/model_adapter.py`): `classify → deterministic_fix → llm_fix → scope_guard → validate → check_progress`, looping back to `classify`. Each failed Gate G4 check becomes a `ClassifiedError`: its fingerprint (`contracts/validation_report.py:fingerprint`, with numbers and ids stripped from the message), a repair code (`repair/policy.py:repair_code`: `DAX_REFERENCE`, `DAX_SYNTAX`, `RECON_MISMATCH`, `FORMAT_STRING_INVALID`, `SOURCE_COLUMN_MISSING`, `REL_DUPLICATE_KEYS`, or the check's own code) and a class from `config/repair_policy.yaml` (read on every call; `max_attempts: 3`, `policy`, `default: user_input`): `deterministic` (code fixes it), `llm` (regenerate only that measure) or `user_input` (escalate). Fixes go into a candidate copy of the ModelSpec: a format-string error drops that format string; a failing measure's DAX is regenerated with `propose_measure_dax` (the failure as feedback, the usual reference pre-check). The scope guard serializes the candidate to a staging folder and compares it with the version in place: if any file other than those of the failing (and touched) objects differs, or nothing differs, the attempt is discarded and still counts. A kept attempt becomes the next `model/v<n>` (and the next ModelSpec version only if the ModelSpec changed: when the deployed files were edited by hand, regenerating them from the ModelSpec is the fix) and is validated, appended to `ValidationReport.json` with `repair_attempt` (`workflow/validate_stage.py:run_validation`; the validation endpoint is the same code plus registration and the move to `MODEL_FAILED`). `check_progress` ends the loop with `passed`, `user_input_only` (only `user_input` errors remain, also before any attempt: no attempts, no model call), `no_progress` (an attempt left the same fingerprints, or none that are new and no fewer) or `limit_reached`; a fix that brings a different error is progress but still counts as an attempt. The graph writes files only; after it returns `repair` registers `TMDLModel`, `ModelSpec` and `ValidationReport` and makes one transition: `passed` to `MODEL_GENERATING`; anything else to `NEEDS_INPUT` (`resume_state: MODEL_FAILED`) with the message (what remains, by class) as the reason and in the result. `workflow/validate_stage.py:Environment` holds what one validation needs, so the loop validates repeatedly. `app/fsutil.py:replace_file` retries a rename that Windows refuses for a moment (a scanner holding a file just written); the stores and writers use it.

### Model validation and Gate G4 (T-504)

`POST /runs/{id}/model/validate` (`workflow/validate_stage.py`, `validate_model`; a plain function) returns `{"report": ValidationRun, "run": RunDetail}`. Allowed in `MODEL_GENERATING` only (`409 WRONG_STATE`); it needs the generated model (`404 NOT_FOUND`), the contract, a scope with a SQL endpoint (`400`), `SANDBOX_WORKSPACE_ID` (`500 CONFIG_ERROR`) and `config/validation.yaml` (`model/validation_config.py`, read on every call: `reconciliation.relative_tolerance` and `absolute_tolerance`; a value matches when `|dax - reference| <= max(absolute, relative * |reference|)`). It reads the current `TMDLModel` folder (`model/tmdl_reader.py`, so what is checked is what is deployed; if the files differ from the generated hash a `G4.REF` warning `FILES_CHANGED` says so), deploys it to the sandbox as `Nexora_<run id prefix>` with `FabricItemsClient`, refreshes it (`connectors/powerbi_api.py`, `PowerBiClient`: workspace-scoped `/groups/{ws}/datasets/{id}/refreshes` polled by request id, `executeQueries` with `includeNulls` and optional `impersonatedUserName`; 429 retried, then an upstream error; a DAX error is a `DaxError` with the engine's text), then runs the checks of `model/validators.py` and appends a `ValidationRun` to `runs/<id>/ValidationReport.json` (`contracts/validation_report.py`; each check has `id`, `object`, `status` pass/fail/warning/skipped, `severity`, `code`, `message`, `evidence` and a `fingerprint`; `classification` stays null for T-505) and registers the artifact `ValidationReport` (`passed`/`failed`). Any failed check moves the run to `MODEL_FAILED`; otherwise it stays in `MODEL_GENERATING` for the review of T-507. `MODEL_FAILED` can only return to `MODEL_GENERATING`, so no report-stage endpoint can accept it.
- **G4.REF:** every measure's DAX references, relationship ends and hierarchy levels exist in the TMDL files.
- **G4.REL:** per relationship, on the sources over the SQL endpoint: duplicate keys on a `one` side fail, an orphan rate above `config/relationship_thresholds.yaml`'s `medium.orphan_rate_max` fails, any orphans warn; queries are in the evidence.
- **G4.DAX:** `EVALUATE ROW("v", [Measure])` per measure; an error fails with the engine's text; a blank result is a warning, or a failure if the KPI has a numeric `expected_examples` value. A refresh or deployment that Fabric rejects fails `G4.DAX` (`REFRESH_FAILED`, `DEPLOY_FAILED`) and marks `G4.REL`, `G4.RECON` and `G4.RLS` `skipped`.
- **G4.RECON:** per measure, the total (and the first label, by sort order, of one slice) against an independent SQL (`model/recon_sql.py`): the model writes it from the KPI definition and the source tables' names and types, never the DAX or any data (`get_recon_llm`, strict JSON schema, 2 attempts); code accepts only one read-only `SELECT` over inventory tables with no literal the definition doesn't state. Both queries and both values, and the difference, are in the evidence. A single numeric `expected_examples` value is compared with the DAX total too; several are shown for review; none gives the note "no business example provided". No usable SQL reference fails the check (`RECON_REFERENCE_UNAVAILABLE`), unless a business example matched, which makes it a warning. Accepted SQL is kept in `recon_suggestions.json` (replayed for an identical request).
- **G4.RLS:** no roles pass ("no roles defined"). A ModelSpec role must exist in the TMDL (`definition/roles/*.tmdl`, which the generator doesn't write yet, so a role from the contract fails with `RLS_ROLE_MISSING` until the filter is supplied), its filter must reference existing columns, and `COUNTROWS` with the signed-in user as the effective identity must be lower than without (equal is a warning).

The API's app registration needs the delegated Power BI permission `Dataset.ReadWrite.All` (with consent) for the OBO call.

### DAX measures (T-503)

`POST /runs/{id}/model/measures` (`workflow/measure_stage.py`, `add_measures`) returns `{"measures": [{"name", "dax", "status": "accepted"|"rejected", "reason"}], "version"}`; `version` is the TMDL version that includes the accepted measures. Allowed in `MODEL_GENERATING` only (`409 WRONG_STATE`); it needs the generated model (`404 NOT_FOUND` before `/model/generate`), the contract and a ModelSpec whose hash is still the approved one (`409 STALE_VERSION`). The run state never changes. For each ModelSpec measure (one `dax_measure` graph invocation each, `graphs/dax_measure.py`, `propose_dax → precheck_references → (one retry with the errors)`, 2 attempts) the model (`get_dax_llm`, strict JSON schema; sees the KPI definition and the ModelSpec's table, column and measure names and types, never data) drafts a `DaxProposal`. `model/dax_generator.py` holds the rules and `propose_measure_dax(kpi, spec, llm, measure_name)`, which returns the proposal or raises `DaxRejected(reason)`. Code reads every `'Table'[Column]` and `[Measure]` out of the DAX text (comments and strings ignored) and rejects the proposal for: an unknown table, column or measure; an unqualified column; a measure that refers to itself; `referenced_objects` that differs from the text; the `/` operator (use `DIVIDE`); a number other than 0 or 1, or a text literal, that the KPI definition doesn't state; time logic or a time-intelligence function with no table of role `date` (`date table required`, and with time logic the model isn't asked at all). A rejected measure keeps its previous DAX (none for a new one) and never gets invented DAX. A timeout, content-filter rejection or unusable output also rejects only that measure. If anything changed, ModelSpec.yaml becomes the next version (copy in `plans/`, the artifact stays `approved` with the new hash; the DAX is approved with the model at G4), each accepted measure's description quotes the approved definition (`Approved: <formula intent>` plus grain, filters, time logic and exclusions), and `write_model_version` writes the next TMDL folder. Accepted answers are kept in `dax_suggestions.json` keyed by a hash of the request, so a repeat call with unchanged inputs makes no model call and no new version.

### TMDL generator (T-502)

`POST /runs/{id}/model/generate` (`workflow/model_stage.py`, `generate_model`; a plain function, deterministic, no LLM) returns `{"version", "files", "run"}` (`files` are relative to `runs/<id>/model/v<version>/`). It is allowed in `PLAN_APPROVED` (`MODEL_FAILED` too when the repair service calls it with `from_repair=True`; `409 WRONG_STATE` otherwise) and moves the run to `MODEL_GENERATING`. `write_model_version` (also behind `python -m app.cli model generate runs/<id>`, which changes no state) needs an approved `ModelSpec` artifact (`404 NOT_FOUND`), a scope with a SQL endpoint (`400 BAD_REQUEST`), a `ModelSpec.yaml` whose hash is still the approved one (`409 STALE_VERSION`) and a passing plan validation (`422 VALIDATION_ERROR` naming each failed PLAN check and path). It writes the next `model/v<n>/` through a staging folder, so an existing version is never modified, and registers the artifact `TMDLModel` (`draft`, `based_on` the ModelSpec hash, hash over every file). `model/tmdl_generator.py` (`generate_tmdl(spec, out_dir, connection)`) writes `definition.pbism`, `definition/{database,model,relationships,expressions}.tmdl` and `definition/tables/<Table>.tmdl`: objects sorted by name (hierarchy levels keep their order), LF, tabs, `lineageTag = uuid5(namespace, run_id/object path)`, names quoted when they aren't plain identifiers, measures with a null `dax` left out. The shared `DatabaseQuery` expression reads the scope's SQL endpoint (`Sql.Database`); `DirectLake` tables get an `entity` partition on it, `Import` tables an `m` partition. A table without a source, a relationship to a missing column or a name with a line break is a `ModelGenerationError` (`422`), and nothing is written. RLS roles and the optional MCP writer are not generated yet.

### Sandbox deployment client (T-501)

`deploy/fabric_items.py` (`FabricItemsClient`; no API route yet, the CLI `deploy model` is the entry point) creates or updates a semantic model from a TMDL folder (`definition.pbism` plus every file under `definition/`, sent as `InlineBase64` parts). `upsert_semantic_model(workspace_id, display_name, tmdl_dir)` lists the workspace's items, matches the name ignoring case, then calls `updateDefinition` (`operation: updated`) or creates (`created`), so a repeat deployment leaves one item. A `202` is polled through `wait_for_operation` (honours `Retry-After`; `FabricTimeout` after 600 s, item state unknown). A failed operation or a `400` is a `FabricOperationFailed` carrying Fabric's error unchanged in `details` plus the request ID; `429` is retried 5 times. A same-named item of another type is `NameConflict` (`409 NAME_CONFLICT`). The target guard lives inside the client: any workspace other than `SANDBOX_WORKSPACE_ID` (falling back to `FABRIC_SANDBOX_WORKSPACE_ID`) is `TargetNotAllowed` (`403 TARGET_NOT_ALLOWED`), and no setting at all is `CONFIG_ERROR`. Only the promotion service (T-702) may build the client with `allow_any_workspace=True`. The token comes from a `token_provider` (default `get_token(FABRIC_SCOPE)`, the CLI's sign-in; the API will pass the user's OBO token).

## Architecture

A staged discovery pipeline. There is no orchestrator or entry point yet; the `test_*.py` scripts wire the stages together by hand. Data flows between stages as plain dicts or the `RequirementSpec` pydantic model:

1. `llm/requirement_analyzer.py` — `analyze_requirement()` returns a `RequirementSpec` (objective, entities, metrics, dimensions, filters, security requirements, assumptions, clarification questions).
2. `connectors/fabric_lakehouse.py` + `discovery/metadata_inventory.py` — `build_metadata_inventory()` returns `{schema_name, tables: [{table_name, columns: [{name, data_type}]}], errors}`. It reads the OneLake table REST API with a bearer token for `storage.azure.com`.
3. `discovery/requirement_data_matcher.py` — deterministic matching of requirement terms to inventory columns, driven by `config/glossary.yaml` (`discovery/glossary.py`) and name normalization.
4. `discovery/semantic_mapper.py` — LLM-suggested mappings and join relationships, given the requirement and the inventory.
5. `discovery/relationship_validator.py` — checks the suggested relationships against the inventory. With `run_data_checks=True` and a connector, it also checks them against real data.
6. `connectors/fabric_sql_connector.py` — a separate read-only path to the Fabric SQL endpoint (pyodbc; passes a `database.windows.net` access token via `attrs_before={1256: ...}`). Used by `discovery/data_profiler.py` and the data checks in step 5.

Design rule stated in the code: **inventory metadata is the source of truth** for which tables and columns exist. LLM output is only a candidate until validated, so don't let LLM-suggested names bypass the validator.

### LLM access

`llm/client.py` builds one shared `OpenAI` client pointed at Azure's v1 endpoint (`{AZURE_OPENAI_ENDPOINT}/openai/v1/`). It uses the Responses API (`client.responses.create`) with `model=AZURE_OPENAI_DEPLOYMENT`. Prompts name the assistant "Nexora"; `ask_rayfin()` is the generic helper. The analyzer and mapper ask for JSON and validate it (pydantic for the analyzer).

## Gotchas

- Table and column names are hardcoded in several places for the sample data (`saleslt.SalesLT_Product`, `saleslt.synthetic_sales_daily`, `data_profiler.py`). Generalizing means touching all of them.
- `.env` holds real credentials and is gitignored (`.env.example` lists the variable names).
